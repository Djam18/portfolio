APIを構築するのは、最初の本番インシデントが起きるまでは簡単に見えます。ほとんどのバグは複雑ではありません — 同じ6つのミスが何千ものコードベースで繰り返されているだけです。ここではそれらを、具体的な修正方法とともに紹介します。

---

## 1. 誤ったHTTPメソッドの使用

最もよく見られるミスです。リソースを削除するために`GET`を使ったり、「動くから」という理由で何でも`POST`を使ったりすることです。

```http
# ❌ GETで削除 — ブラウザがこのURLをプリフェッチした場合に致命的
GET /api/users/42/delete

# ✅ 正しい方法
DELETE /api/users/42
```

HTTPメソッドには、クライアント、プロキシ、キャッシュが依存する意味的な意味があります。`GET`は冪等かつ安全（副作用なし）でなければなりません。`POST`は作成、`PUT`/`PATCH`は更新、`DELETE`は削除です。これらの規約に違反すると、キャッシュ、ブラウザの履歴、そして仕様に従うすべてのHTTPクライアントが正しく動作しなくなります。

---

## 2. 誤ったステータスコード

エラーレスポンスに`200 OK`を返すことは、初心者APIで最もよく見られるミスです。

```json
// ❌ ステータス200、でもエラー
{
  "success": false,
  "error": "ユーザーが見つかりません"
}

// ✅ ステータス404 — ボディを解析せずともクライアントはすぐに分かる
{
  "error": "ユーザーが見つかりません",
  "code": "USER_NOT_FOUND"
}
```

**最も重要なステータスコード：**

| コード | 使用する場面 |
|--------|-------------|
| `200` | ボディありの成功 |
| `201` | リソース作成（POST） |
| `204` | 成功、ボディなし（DELETE） |
| `400` | クライアントからの無効な入力 |
| `401` | 未認証 |
| `403` | 認証済みだが未承認 |
| `404` | リソースが存在しない |
| `422` | 構文的には正しいが意味的に誤った入力 |
| `429` | レート制限超過 |
| `500` | サーバーエラー（クライアントの責任ではない） |

## 3. クライアント入力を信頼する

クライアントから送信されるすべての値は、潜在的な攻撃ベクトルです。

```php
// ❌ 絶対にやってはいけない
$id = $_GET['id'];
$query = "SELECT * FROM users WHERE id = $id";
// SQLインジェクション: ?id=1 OR 1=1

// ✅ 常にバリデーションとサニタイズを行う
$id = filter_var($_GET['id'], FILTER_VALIDATE_INT);
if (!$id) {
    return response()->json(['error' => '無効なID'], 400);
}
$user = User::findOrFail($id); // パラメータ化クエリ
```

バリデーション：型、フォーマット、長さ、範囲。データベースやファイルシステムの操作前にサニタイズ。リクエストボディ、ヘッダー、クエリ文字列に含まれるものを決して信頼しないこと。

## 4. 機密データの漏洩

フィルタリングなしでデータベースオブジェクト全体を返すことは、データ漏洩への招待です。

```json
// ❌ 生のUserモデルを返す
{
  "id": 42,
  "email": "user@example.com",
  "password": "$2b$12$...",
  "stripe_customer_id": "cus_xxx",
  "internal_notes": "要確認としてフラグ立て済み",
  "created_at": "2024-01-01"
}

// ✅ クライアントが実際に必要なものだけを返す
{
  "id": 42,
  "email": "user@example.com",
  "created_at": "2024-01-01"
}
```

シリアライザー、DTO、またはAPI Resources（Laravel）を使用して、公開するものを明示的に定義する。ルール：**オプトイン、オプトアウトではない。** 何も公開しない状態から始め、必要なものだけを追加する。

---

## 5. 一貫性のないエラーフォーマット

各エンドポイントが異なる形式でエラーを返すと、各クライアントがすべての形式を処理しなければなりません。

```json
// ❌ エンドポイントA
{ "message": "見つかりません" }

// ❌ エンドポイントB
{ "error": true, "msg": "バリデーション失敗", "fields": ["email"] }

// ❌ エンドポイントC
"内部サーバーエラー"

// ✅ 1つのフォーマット、すべての場所で
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "リクエストに無効なフィールドが含まれています。",
    "details": [
      { "field": "email", "issue": "メールフォーマットが無効" }
    ]
  }
}
```

エラーエンベロープを一度定義する。グローバルな例外ハンドラーを通じてすべての場所に適用する。クライアント — 自分自身のフロントエンドも含めて — が感謝するでしょう。

---

## 6. APIバージョニングなし

エンドポイントのレスポンスを変更すると、それを使用しているすべてのクライアントが壊れます。バージョニングなしでは、APIは決して進化できません。

```http
# ❌ バージョンなし — 破壊的変更がすべてのクライアントに即座に影響する
GET /api/users

# ✅ バージョン管理済み — v1は安定したまま、v2が安全に破壊的変更を導入できる
GET /api/v1/users
GET /api/v2/users
```

v1しかなくても、最初からバージョニングする。クライアントが本番環境にある後で`/v1/`を追加するコストは、最初から含めるコストよりもはるかに高くなります。

---

## まとめ

これらのミスを修正するのに高度な知識は必要ありません。必要なのは規律です：各エンドポイントをリリースする前のチェックリスト。

- [ ] HTTPメソッドが操作のセマンティクスと一致している
- [ ] ステータスコードが正確である
- [ ] すべての入力が使用前にバリデーションされている
- [ ] レスポンスが必要なフィールドのみを公開している
- [ ] エラーがグローバルフォーマットに従っている
- [ ] URLにAPIバージョンが含まれている
